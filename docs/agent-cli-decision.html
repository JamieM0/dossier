01 /

Decision

Dossier will ship a local service and CLI. The service owns encrypted CLI profiles and exposes the shared Dossier application actions through a CLI adapter.

Use one action layer. The CLI and GUI can call shared use cases through separate adapters. The CLI service uses its own profile store and credentials.

Share work

Shared CLI profiles

Every CLI client uses the same profile namespace through the local service. A profile update becomes visible to the next CLI read.

Keep a hard line

GUI data stays separate

The CLI service has its own data root and key. Its API has no GUI-store path or GUI-profile operation.

Avoid repeated work

Actions are the source of truth

Each supported action has one implementation, schema, help entry, and output contract. The CLI does not reproduce UI logic.

The CLI covers Dossier data actions, profile operations, settings, export, and import. Destructive actions use explicit confirmation or flags.

02 /

What exists today

The current product has one GUI library. This record adds a separate CLI profile model; it does not add GUI profile selection.

Important distinction: the current app has one persisted library, not a profile manager. A CLI profile is a new storage namespace. The GUI will not list, open, or manage CLI profiles.

03 /

Alternatives considered

Dossier selected a local service and CLI. The other options did not meet the privacy, sharing, or maintenance goals.

OptionHow clients shareStrengthsCosts and limits
Encrypted file + CLICLI clients point at one file and unlock key.Small first build. Works offline. Reuses file encryption and portable exports.Concurrent writes need locking and recovery. Every client can parse the store. This option gives Dossier a weaker service boundary.
Local service + CLI SelectedA local service owns the CLI store. CLI clients call it through a local socket.One writer path, clean API boundary, shared state across clients, and room for multiple adapters. The GUI store stays outside the service.Adds a service lifecycle, socket permissions, profile locking, and local client authorization to maintain.
Cloud sync serviceCLI clients authenticate to a hosted profile endpoint.Cross-machine access and central concurrency controls.Creates a network service, identity system, hosting and breach risks. Conflicts with the current local-first model and raises operating costs.

Why a local service

Share state without file races

One service owns each CLI profile and applies writes in order. Multiple CLI processes read and update the same current state without coordinating file writes themselves.

Local-only access

Remote access stays out of scope

The local service shares profiles among CLI clients on this machine. Network access is not part of this decision.

04 /

Make the privacy boundary real

The CLI service uses a separate path and key. This application-level boundary is the agreed protection for CLI profiles.

Desktop applicationGUI profile store

Existing app data root · existing keychain key · GUI and its paired mobile clients

×
CLI serviceCLI profile store

Separate data root · separate key namespace · CLI clients only

Storage isolation

  • Choose a dedicated CLI data root, such as ~/Library/Application Support/Dossier/cli.
  • Store profiles under stable IDs, not names used as file paths.
  • Use a separate encryption key for every store boundary. Never reuse the GUI master key.
  • Keep CLI data out of GUI import, reset, sync, and mobile gateway operations.

Local access

  • Bind to a Unix domain socket. Do not listen on a network interface by default.
  • Set restrictive socket and directory permissions. Authenticate the local client.
  • Keep secrets out of arguments, shell history, logs, and standard output.
  • Write audit events for profile creation, imports, deletion, and key changes without taste content.

Agreed scope for “no access whatsoever”. The CLI has no application path, API, or key for GUI data. This app-level boundary is sufficient for this decision. Protection from hostile code under the same OS account is outside scope.

The service keeps one CLI-wide credential vault for TMDB and other CLI integrations. Every CLI profile can use those credentials. The vault uses a key separate from the GUI keychain entries.

Completeness comes from shared application actions and their registry. The CLI adds an adapter, not a second implementation of each feature.

Definition of complete: every product action appears in the registry with a CLI adapter or a recorded reason for exclusion. The CLI exposes machine-readable help for runtime discovery.

Rendering, drag gestures, posters, animation, and window controls are interface behavior. Their data outcomes map to shared actions; visual mechanics need no CLI equivalent.

06 /

Keep CLI output small

The CLI returns compact JSON by default. It bounds result sizes and uses stable references to reduce output tokens.

Output contract

  • Return JSON by default. Offer --readable for people.
  • Return only requested fields. Use compact names and omit empty metadata.
  • Use limits and cursors for queues, library lists, and recommendations.
  • Return item IDs and short titles first. Add summaries or evidence only on request.
  • Send diagnostics to stderr. Reserve stdout for result data.
  • Keep error codes stable and messages short, with a next action when possible.

Interaction model

  • Make operations composable: list IDs, inspect one ID, then update it.
  • Support --fields, --limit, and --cursor.
  • Support NDJSON for large exports or streaming result sets.
  • Provide --dry-run for imports and bulk changes.
  • Read passphrases through a hidden prompt or standard input, never an argument.
  • Keep help concise and expose schemas through help --json.
Compact response example
{
  "items": [
    {"id":"movie:27205","title":"Inception","year":2010,"score":0.84},
    {"id":"movie:157336","title":"Interstellar","year":2014,"score":0.81}
  ],
  "next":"c_7f2a"
}

Do not send full evidence, feature vectors, poster URLs, or complete profile state in every response. A dedicated explain or profile-inspect action can return those fields when requested.

07 /

CLI surface

The CLI exposes Dossier commands directly. JSON is default; people can add --readable for tables.

Example CLI commands
dossier profile create research
dossier profile list
dossier profile use research

dossier rate queue --mode active --limit 5
dossier rate set movie:27205 --value 3

dossier taste claims --limit 10
dossier taste claim confirm claim:genres:science-fiction

dossier suggest --medium movie --limit 8
dossier suggest explain movie:157336

These examples operate on CLI profiles. The CLI does not connect to the GUI service or GUI library.

Ship the profile boundary and a useful CLI slice first. Expand coverage through the capability registry and preserve one action implementation.

Registry parity

When needed

09 /

Consequences and constraints

These consequences follow from the accepted decisions and guide implementation.

!
App-level isolation

The CLI has no API, store path, or key for GUI data. Hostile local code under the same OS account is outside the accepted threat model.

!
CLI-wide credentials

TMDB and future integration credentials belong to one CLI credential vault shared by every CLI profile. They remain separate from GUI credentials.

!
No GUI profile support

The GUI remains a single-profile interface. CLI profile data stays out of the GUI.

!
Profile operations

Profile deletion, reset, and import replacement need confirmation, dry-run, backups, and clear recovery behavior.

!
Concurrent edits

Use optimistic concurrency control. Each profile read returns a revision. Each mutation supplies its expected revision. The service rejects stale writes; clients refresh and retry.

!
Shared local service

All CLI clients read and update the same profile store. The GUI uses its existing store and service.

Accepted record

Decision status: accepted

Dossier will provide a local service and CLI with separate encrypted profiles, one shared CLI credential vault, and application-level isolation from GUI data.

  • Use one shared action layer and registry for CLI and GUI capabilities.
  • Use optimistic concurrency control for edits made from stale profile state.
  • Keep CLI profiles out of the GUI. The GUI will not support multiple profiles yet.

Basis: repository review of README, VISION, desktop backend, remote gateway, encrypted store, domain model, and current UI routes and state modules. This record captures architecture decisions; it does not change runtime behavior.
